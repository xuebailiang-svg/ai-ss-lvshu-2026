# 高德 + 人工补充 + AI 报告 MVP 实施计划

> 文档状态：Phase A–H 已实施，Phase I 待部署环境真实验收
> 对应 PRD：`docs/PRD_AMAP_MANUAL_AI_MVP.md`
> 当前阶段限制：本文件只规划，不修改业务代码、数据库、前端、API、部署或 Git 历史。

## 1. 实施目标

把当前功能较多、链路并行的系统收敛为一条稳定、诚实、普通投资者可理解的主流程：

```text
创建项目
→ 高德地理编码与 POI 采集
→ 查看高德结果并人工补充
→ 数据检查
→ AI 最多两轮重要提问
→ 基于最终快照生成报告
```

实施不追求增加数据源或算法，而是减少复杂度、消除平行链路、修复真实性边界并完成真实业务验收。

## 2. 当前代码审计结论

## 2.1 可直接复用的基础

- `site_projects` 已是当前项目主表。
- `pois`、`competitors`、`food_businesses`、`entertainments` 已有统一记录。
- 高德已有地理编码、周边查询、转换和分类采集服务。
- 竞品、配套、租金已有列表、详情、更新和审核基础。
- 人工输入已有历史记录机制。
- `AIReportRecord` 已保存 `input_snapshot`，适合报告可追溯。
- DeepSeek 与系统配置已经存在数据库优先、环境变量备用的读取逻辑。
- `MarkdownReport` 已支持 Markdown 展示，可继续承载导出和打印。

## 2.2 必须收敛的重复或冲突

- 新 `site_projects` 与旧 `site_evaluations` 两套项目链路并存。
- `Workbench` 与 `ProjectDetail` 两套流程页面并存。
- 主工作台当前为 8 步，并混入爬虫、评分、聊天和报告。
- 旧 Agent、Evaluation、History、Reports 路由仍可直接访问。
- `main.py` 注册大量不属于 MVP 的路由。
- `SystemConfig` 同时管理爬虫、政府数据、第三方、评分和 Memory。
- `data_quality` 混合爬虫、政府数据、模拟数据和评分罚分。
- AI 上下文混合 score、city insight、memory、crawler evidence 和 simulation。
- AI review 是 Markdown 审核结果，不是受控的结构化补充提问。

## 2.3 当前发布基线阻塞项

正式进入产品改造前必须先处理：

1. `0014_backfill_amap_business_hours` revision 超过 Alembic 默认 32 字符限制；线上曾通过手工改名为 `0014_amap_hours`，本地迁移历史必须形成一致且可重复的修复策略。
2. 从零建库、现有生产库升级和 `alembic current/heads` 必须同时验证，禁止再次用服务器手工 `sed` 形成与 Git 不一致的迁移图。
3. 部署诊断必须查询真实表名 `site_projects`，不能用不存在的 `projects` 表误判数据库为空。
4. 先建立数据库备份和迁移演练，再开始删除或停用任何旧模块。

## 3. 总体策略

### 3.1 顺序原则

1. 先确认基线可安装、可测试。
2. 先隐藏无关 UI 和入口，不立即删除数据表。
3. 再稳定高德与人工补充主数据链路。
4. 再简化数据检查和 AI 上下文。
5. 最后统一页面、做真实地址验收。
6. 新流程稳定后另开清理任务删除旧模块。

### 3.2 兼容策略

- `site_projects` 作为唯一新流程项目表。
- 旧数据只读保留，不继续扩展旧 Evaluation API。
- 旧路由先重定向或返回明确停用提示。
- 爬虫、政府数据、Memory 等先从 UI 和 AI 快照排除，暂不删表。
- 数据库结构变更必须单独迁移并带升级/回滚测试。

### 3.3 完成定义

每个 Phase 必须同时满足：

- 代码范围与 PRD 一致。
- 相关自动化测试通过。
- 不引入真实密钥或模拟事实。
- 用户界面没有技术概念泄漏。
- 文档和部署说明同步。
- 用户确认阶段验收后才进入下一 Phase。

## 6. Phase C：高德采集链路整理

> 实施状态：已完成。实现与验收说明见 `docs/PHASE_C_AMAP_COLLECTION.md`。

### 6.1 目标

让“地址 → 坐标 → 分类 POI → 统一记录 → 可理解结果”成为完整、透明、可重试的唯一自动采集链路。

### 6.2 修改范围

- 统一创建项目时的地理编码流程和错误提示。
- 支持歧义地址候选确认，避免静默选择错误坐标。
- 为每个关键词增加受控分页，不再固定只取第一页。
- 设置每分类最大页数/最大记录数，达到上限时明确标记截断。
- 统一跨关键词去重规则，优先使用高德 POI ID，缺失时使用名称 + 地址 + 坐标。
- 保存原始返回数量、有效数量、唯一保存数量、失败关键词和采集时间。
- 审计高德真实响应后映射电话、评分、营业时间和营业状态；不存在就保持空。
- 明确“疑似竞品”分类，不自动确认其真实经营状态。
- 防止重复采集产生重复业务记录；重新采集更新高德字段但不覆盖人工补充。
- 将 API 结果改为业务化统计和诊断，不返回长原始 JSON 给前端。

### 6.3 不修改范围

- 不接入其他地图或第三方数据源。
- 不调用爬虫补详情。
- 不估算人口、客流和消费能力。
- 不修改 AI 报告。

### 6.4 预计文件

- `backend/app/map_data/service.py`
- `backend/app/map_data/mapper.py`
- `backend/app/map_data/router.py`

- 前端 Step 2/3 相关组件和 API 类型

### 6.5 验收条件

- 示例地址能正确地理编码。
- 每个分类按配置分页并能停止。
- 跨关键词重复 POI 只保存一条。
- 接口返回展示数量与数据库唯一数量一致。
- 能区分：成功有数据、成功零数据、部分失败、完全失败、达到上限。

## 7. Phase D：人工补充模型与界面整理

> 实施状态：已完成（2026-08-12）。实现与验证记录见 `docs/PHASE_D_MANUAL_REVIEW.md`。

### 7.1 目标

让人工调查围绕高德已发现对象完成，减少空白表单和重复记录，只保留真正影响电竞馆选址的字段。

### 7.2 修改范围

- 统一 `ProjectSupplement` 和旧数据采集中心的重复功能。
- 高德字段只读展示；人工字段按业务分组编辑。
- 竞品列表默认按距离排序，突出最近/核心竞品。
- 支持“只看待补充”和名称搜索。
- 竞品补充保留：有效性、机器数、面积、CPU/GPU/显示器、小时价、会员价、营业时间修正、开业时间、充值活动、现场上座率及观察上下文、备注。
- 营业额仅作为有可靠来源时的可选字段，不进入必填和准备度。
- 餐饮/娱乐只补有效性、营业时间、夜间/24 小时现场确认、备注。
- 候选物业表单保留面积、月租、楼层、用途、供电、消防、网络、独立入口等核心字段。
- 写入字段来源、核实时间和人工修改历史。
- 用户可以明确选择“不知道”，不强迫填写。
- 评估是否需要受控的“高德未收录对象”入口；若第一版实现，必须标记人工新增且与高德对象区分。

### 7.3 不修改范围

- 不让 AI 自动填写人工字段。
- 不恢复爬虫建议或第三方证据。
- 不要求用户填写人口、消费或盈利预测。
- 不自动确认所有高德候选。

### 7.5 验收条件

- 从某条高德竞品打开补充时，名称、地址、距离已存在且不重复填写。
- 保存后仍是同一条竞品记录。

## 8. Phase E：数据核验与准备度机制

> 实施状态：已完成（2026-08-12）。实现与验证记录见 `docs/PHASE_E_READINESS.md`。

### 8.1 目标

替换当前混合多数据源和复杂罚分的质量逻辑，输出普通业务人员能理解的事实清单和缺失分级。

### 8.2 修改范围

- 定义固定的数据检查目录和透明权重。
- 区分技术前置条件、关键未知、建议补充和可选信息。
- 检查高德采集是成功零结果还是请求失败。
- 竞品数量使用疑似竞品事实；核心竞品信息按距离和有效性检查。
- 营业额、人口、热力和外部租金不列为必填。
- 输出结构化 `readiness`，前端只呈现业务语言。
- 将 crawler、government、simulation、memory、复杂评分从数据检查响应和页面中排除。
- 报告生成守卫：技术前置不完整时只能生成“数据不足”报告。

### 8.3 不修改范围

- 不重新设计复杂评分模型。
- 不把准备度解释为推荐概率。
- 不用 AI 计算准备度。
- 不阻止用户带着普通缺失生成报告。

### 8.4 预计文件

- `backend/app/projects/service.py`
- `backend/app/projects/schemas.py`
- `backend/app/projects/router.py`
- 可新增 `backend/app/data_quality/` 简化模块
- 项目详情 Step 4 组件
- `backend/tests/test_data_quality.py`
- 前端数据核验测试

### 8.5 验收条件

- 同一项目重复检查结果稳定。
- 页面明确显示已完成、关键未知、建议补充、可选。
- 准备度能解释到具体检查项。
- 缺少营业额不降低关键准备度。
- 没有执行高德采集与采集成功但零结果得到不同结论。
- 响应和页面不含内部技术字段。

### 8.6 测试内容

- 空项目、只地理编码、完整高德、部分人工、完整人工等数据组合。
- 真零结果与失败结果。
- 未知回答不重复标红。
- 准备度计算边界和舍入。
- 报告生成守卫。

## 9. Phase F：AI 缺失信息提问

> 实施状态：已完成（2026-08-12）。实现与验证记录见 `docs/PHASE_F_AI_QUESTIONS.md`。

### 9.1 目标

把现有 Markdown AI 审核改为一次或两次、可验证、能写回项目的结构化重要问题流程。

### 9.2 修改范围

- 在调用 AI 前由系统生成允许提问的缺失字段目录。
- 创建严格的结构化输出 schema。
- Prompt 限制 AI 只能选择目录内字段，不得编造新指标。
- 后端验证字段确实缺失、未问过且可由用户回答。
- 默认一轮、最多两轮；每轮最多 3 题，总计最多 5 题。
- 支持文字、数字、金额、布尔、单选以及“不知道 / 暂不提供”。
- 回答写入对应业务字段或问题回答记录，并标记 `USER_PROVIDED`。
- 未知回答写入 `UNKNOWN` 原因，后续不再追问。
- 复用现有 `/ai-review` 能力还是增加专用端点，须在实现前以最小变更原则确认；不同时保留两套对用户可见流程。

### 9.3 不修改范围

- 不开放无限聊天作为报告前置。
- 不让 AI 写入没有用户回答的数据。
- 不问人口、消费能力、客流、盈利等问题。
- 不调用外部网络或工具。

### 9.4 预计文件

- `backend/app/llm/service.py`
- `backend/app/llm/prompts.py`
- `backend/app/llm/schemas.py`
- `backend/app/llm/router.py`
- AI 问答记录模型/迁移（仅在现有字段无法承载时）
- 项目详情 Step 5 组件
- 前端 API 类型与表单组件
- `backend/tests/test_ai_questions.py`

### 9.5 验收条件

- 无重要缺失时返回空问题并进入报告。
- 有重要缺失时只问相关、可回答的问题。
- 已存在字段不被重复询问。
- 达到两轮或用户跳过后停止。
- “不知道”被持久化且不会触发循环。
- 模型返回非法 JSON 或越界问题时，系统安全降级为跳过提问，而不是阻塞报告。

### 9.6 测试内容

- 0、1、3、超过 3 个缺失候选。
- 两轮上限和总问题上限。
- 重复字段、非法字段、已知字段拦截。
- 模型超时、无效 JSON、空响应。
- 用户答案校验和写回。
- 未知与跳过状态。

## 10. Phase G：AI 报告真实性重构

> 实施状态：已完成（2026-08-19）。实现与验证记录见 `docs/PHASE_G_REPORT_TRUTHFULNESS.md`。

### 10.1 目标

让报告只读取高德事实、人工事实、AI 提问后的用户答案和确定性计算，任何数字可追溯。

### 10.2 修改范围

- 新建唯一 `final_project_snapshot` 构建器。
- 只包含允许的 `confirmed/有效` 主链路数据和字段级来源。
- 排除 raw_data、confidence、crawler、government、memory、simulation、旧 score 和 rejected 数据。
- 在报告生成时固化快照版本、生成时间和数据准备度。
- 简化 Prompt 为 PRD 八章固定结构。
- 将 `UNKNOWN`、来源边界和禁推测规则写入 system prompt。
- 增加确定性输出校验：报告出现的数字必须能在快照中匹配；无法验证时拒绝发布并重试一次受限生成或显示错误。
- 推荐等级增加后端守卫：关键前置不足时强制“数据不足”。
- 重新生成创建新报告版本，不覆盖旧快照。
- 报告底部列出数据来源说明和现场核实清单。

### 10.3 不修改范围

- 不让 AI 调用互联网。
- 不输入政府数据、爬虫证据、Memory 或模拟数据。
- 不预测营业额、利润、客流或回本。
- 不增加复杂评分和城市排名。

### 10.4 预计文件

- `backend/app/llm/service.py`
- `backend/app/llm/prompts.py`
- `backend/app/llm/schemas.py`
- 可新增 `backend/app/llm/snapshot.py`
- `backend/app/models/entities.py`（若报告版本字段不足）
- 对应 migration（只有必要时）
- `frontend/src/components/MarkdownReport.tsx`
- 报告展示/导出组件
- `backend/tests/test_ai_report.py`
- 快照与 Prompt 契约测试

### 10.5 验收条件

- `input_snapshot` 只包含允许的数据。
- 每个字段可识别 `AMAP_PROVIDED`、`USER_PROVIDED`、`CALCULATED` 或 `UNKNOWN`。
- 数据不足项目不会输出“推荐”。
- 没有上座率时报告明确无法判断经营热度。
- 没有人口数据时不描述本地年轻人口。
- 没有租金时不判断租金高低。
- 报告固定八章且适合投资者阅读。
- HTML 和打印 PDF 包含完整正文、来源与核实清单。

### 10.6 测试内容

- 快照白名单和敏感字段排除。
- 来源标签与未知值。
- Prompt 禁止词和真实性约束。
- 报告数字追溯校验。
- 完整数据、部分数据、极少数据三类报告。
- 模型超时、返回空内容、违规数字和无效结构。
- 报告版本不被后续项目编辑污染。

## 13. Phase 后的遗留清理（需另行确认）

Phase A–I 完成并稳定运行后，再单独提交“删除旧模块”计划。删除前必须满足：

- 生产数据已备份。
- 旧路由连续一个版本无访问或已完成迁移。
- 新流程具备等价的合法业务能力。
- 全项目引用扫描为零。
- Alembic 删除表/字段迁移有明确回滚或归档策略。

候选清理对象：

- 旧 Evaluation 和 CandidateSite 数据链。
- crawler 与 Worker。
- government stats。
- memory 和 business outcome。
- agent/tool/trace/reflection/demo。
- 动态 scoring config 和不再使用的复杂评分。
- 旧前端页面和重复路由。

这部分不应与 MVP 主流程改造同时执行。

## 14. 阶段依赖与建议节奏

```text
Phase A 发布基线
  ↓
Phase B UI 隐藏
  ↓
Phase C 高德主链
  ↓
Phase D 人工补充
  ↓
Phase E 数据检查
  ↓
Phase F AI 提问
  ↓
Phase G 报告真实性
  ↓
Phase H 六步 UI
  ↓
Phase I 真实验收
```

- Phase A 是所有开发的硬前置。
- Phase C 与 D 数据契约稳定后才能实施 E–G。
- Phase F 与 G 可以共享最终快照契约，但必须分别验收。
- Phase H 在业务接口稳定后统一收口，减少反复改 UI。
- 每个 Phase 建议独立提交、独立测试、独立部署验收，禁止一次合并全部大改。

## 15. 风险与控制

| 风险 | 控制措施 |
|---|---|
| 旧、新项目链路误用 | 明确 `site_projects` 为唯一主链；旧 API 停止新增调用 |
| 迁移历史与生产不一致 | Phase A 先做生产副本迁移演练，不再服务器手改 |
| 高德结果被称为“完整市场数据” | 显示查询范围、关键词、上限、失败和截断 |
| 重采集覆盖人工调查 | 字段来源分层，幂等测试和更新白名单 |
| 用户被大量补充字段劝退 | 只突出最近核心竞品和关键物业字段，允许未知 |
| AI 无限追问 | 后端强制轮次、题数、字段目录和去重 |
| AI 编造数字 | 最终快照白名单、Prompt 约束、数字追溯校验、数据不足守卫 |
| 隐藏模块仍污染 AI | 快照构建器明确排除并用测试锁定 |
| 过早删除旧表造成数据损失 | 先隐藏，稳定后另立清理 Phase |
| 前端再次变成大工作台 | 四页面、六步骤和业务结果归位作为 UI 验收硬标准 |

## 16. PRD 确认后的第一步

用户确认 PRD 后，只启动 Phase A。Phase A 完成后输出：

1. 当前路由/模块/表依赖清单。
2. 迁移一致性修复方案与验证结果。
3. 新旧主链边界。
4. 本阶段修改文件。
5. 自动化测试结果。
6. 是否满足进入 Phase B 的条件。

未获得用户对当前 Phase 的验收确认，不进入下一 Phase，也不顺带开发新功能。
