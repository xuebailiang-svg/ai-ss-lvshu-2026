# 电竞馆智能选址 MVP 产品需求文档

> 文档状态：已确认并进入发布验收
> 产品范围：高德数据 + 人工补充 + AI 报告
> 基线：当前仓库实际代码审计结果
> 本文档只定义产品，不代表相关改造已经实施。

## 1. 产品定位

本版本只解决一个问题：

> 用户提交一个候选电竞馆地址，系统使用高德地图实际返回的数据建立周边事实基础；用户补充高德无法提供但自己掌握的经营与物业事实；系统再让 AI 仅依据这些已保存事实和确定性统计，生成一份可供电竞馆投资者阅读的选址分析报告。

产品不是通用商业选址平台，也不是能够自动获得全部商业情报的系统。它是一套有明确数据边界、允许“不知道”、能把调查过程和报告结论串起来的电竞馆候选地址分析工具。

### 1.1 核心价值

- 把地址、周边 POI、竞品和配套信息快速整理成结构化项目。
- 让人工调查直接补充到高德已发现的对象上，避免重复建档。
- 明确区分高德事实、人工事实、系统计算和未知信息。
- 在资料不完整时仍能输出诚实的“数据不足”报告，而不是编造结论。
- 给投资者一份业务化、可读、可导出的分析报告和现场核实清单。

### 1.2 产品成功标准

普通用户不需要理解 `Provider`、`Agent`、`confidence`、`raw_data`、爬虫或工具调用，即可顺着页面完成一次选址分析。所有报告数字都能够追溯到高德返回、用户输入或确定性计算。

## 2. 目标用户

### 2.1 主要用户

- 准备开设电竞馆的个人投资者。
- 电竞馆连锁品牌的选址或拓展人员。
- 协助投资者进行前期调查的客户经理。

### 2.2 用户特点

- 了解地址、租金、物业和部分竞品情况，但不具备数据工程背景。
- 希望快速知道“目前掌握了什么、还缺什么、下一步查什么”。
- 能接受资料不足，但不能接受系统把估算或常识写成当地事实。
- 需要可以直接阅读、打印或分享的报告。

## 3. MVP 范围

### 3.1 本版本包含

1. 创建、查看和删除选址项目。
2. 高德地理编码，保存候选地址经纬度。
3. 按项目半径采集高德可返回的交通、竞品、餐饮、娱乐及其他有用 POI。
4. 分类展示高德采集结果和采集诊断。
5. 基于高德对象补充竞品、餐饮、娱乐信息。
6. 补充候选物业和实际租金信息。
7. 清晰的数据检查、关键缺失和建议补充清单。
8. 最多两轮、只针对重要缺失信息的 AI 提问。
9. 基于最终项目数据快照生成 AI 选址报告。
10. Markdown 阅读、HTML 导出和浏览器打印 PDF。
11. 系统配置：高德 Web Service Key、DeepSeek API Key、DeepSeek Base URL、DeepSeek Model。

### 3.2 本版本明确不包含

- 任何网页爬虫或搜索发现型爬虫。
- 百度、腾讯、美团、大众点评、贝壳等第三方数据接入。
- 消费热力、人口热力、真实客流或商业 LBS 数据。
- 外部租金自动采集和市场租金估算。
- 多数据源 Provider 扩展和数据源注册中心产品化。
- 复杂 Agent 自动工具编排、Reflection、Trace、Tool Log。
- 长期 Memory、历史经营反馈学习和自动经验沉淀。
- 机器学习预测。
- 营业额、上座率、盈利、回本周期或消费能力预测。
- 基于区域名称推断人口、年龄结构、客流或商圈等级。
- 政府宏观数据、城市洞察和第三方商业数据。
- 对多个候选地址进行自动排名或投资组合优化。

上述模块即使仍存在于代码和数据库中，也不属于 MVP 的用户承诺。

## 4. 核心产品原则

### 4.1 业务流程优先

界面只显示用户任务，不暴露技术实现。以下概念不得出现在普通用户流程：

- Provider / Source Registry
- Agent Trace / Tool Execution / Reflection
- `confidence` / `raw_data`
- crawler / third_party / external heatmap
- debug 日志和异常堆栈

### 4.2 高德是唯一自动外部数据源

高德实际返回什么，系统就保存什么。某字段接口没有返回时必须保持未知，不得根据接口文档中的“可能返回”自行生成。

### 4.3 人工补充依附于已有业务对象

用户为某家竞品补充价格、配置等信息时，必须更新对应的高德竞品记录，不再默认创建一套平行数据。确有高德遗漏对象时，第一版建议通过“现场发现但高德未收录”受控入口新增，并明确标记为人工新增；该入口不应成为常规采集方式。

### 4.4 未知是合法结果

字段为空不是系统错误。用户可以选择“不知道 / 暂不提供”，系统保存为 `UNKNOWN`，AI 不再重复追问，也不能将其推导为事实。

### 4.5 报告不能比数据知道得更多

报告只能使用最终项目快照。AI 不得联网、调用其他数据源、补行业常识数字或把经验判断包装为本地事实。

## 5. 信息架构

MVP 只保留四类核心页面：

1. 首页 / 项目列表
2. 创建选址分析
3. 选址项目详情
4. 系统配置

报告作为项目详情的最后一步展示，不需要独立主导航。必要时可保留只读报告 URL 供分享和打印。

### 5.1 项目详情的六步流程

```text
1 输入地址
  ↓
2 高德采集
  ↓
3 查看并人工补充
  ↓
4 数据检查
  ↓
5 AI 提问
  ↓
6 生成报告
```

每一步是一张独立流程卡片。当前步骤高亮，已完成步骤显示绿色状态，未开始步骤显示完成前置条件。结果直接展示在对应步骤下方，不把业务结果放入聊天日志。

## 6. 完整用户流程与页面交互

## 6.1 Step 1：输入候选地址

### 输入

- 项目名称：可选；为空时由地址生成。
- 城市：必填。
- 详细地址：必填。
- 分析范围：必填，建议选项为 500 米、1000 米、1500 米，自定义值限制在合理范围内。
- 业务类型：固定为“电竞馆”，MVP 不做多业态。

### 操作

用户点击“开始分析”。系统先调用高德地理编码：

- 成功：显示标准化地址和坐标，创建项目并进入 Step 2。
- 返回多个候选：让用户选择匹配地址后创建项目。
- 无结果：提示用户补充区县、道路或建筑名称，不创建错误坐标项目。
- 接口失败：显示业务化错误和重试按钮，保留输入内容。

### 页面反馈

- 不直接显示原始 JSON。
- 坐标只作为地址确认的辅助信息，不要求用户编辑。
- 明确显示分析半径单位为“米”。

## 6.2 Step 2：采集高德数据

### 操作

创建项目后可自动开始采集，也保留一个明确的“获取高德数据”按钮供失败重试。采集过程中显示分类进度，不显示工具日志。

### 完成反馈

```text
高德采集完成
交通：地铁 2、公交站 18、停车场 12
疑似竞品：8
餐饮：56
娱乐：21
```

同时显示：

- 采集时间。
- 分析地址和半径。
- 是否有失败分类。
- 因接口上限被截断的分类提示。

“高德采集完成”只表示请求执行完成，不代表互联网上所有商户都已完整收录。

## 6.3 Step 3：查看并人工补充

页面使用分类标签：

- 交通
- 竞品
- 餐饮
- 娱乐
- 候选物业与租金

每个列表项优先显示名称、距离、地址、类别、营业时间等已有事实。字段旁使用简单来源标记：

- 高德获取
- 人工补充
- 系统计算
- 未填写

点击“补充详情”打开侧边抽屉或对话框。高德已有字段只读，人工字段可编辑，保存后即时更新完整度状态。

竞品数量多时支持按距离排序、名称搜索和“只看待补充”。不要求用户逐条补齐全部竞品；页面突出距离最近和最相关的核心竞品。

## 6.4 Step 4：数据检查

用户点击“检查数据”后看到业务化结果：

```text
数据准备度：76%

已完成
✓ 候选地址与分析范围
✓ 高德采集已完成
✓ 已发现 8 家疑似竞品

建议补充
△ 最近 3 家竞品尚无价格
△ 最近 2 家竞品尚无机器数量

关键未知
○ 候选物业月租金
○ 候选物业可用面积
```

数据检查不因为任何一个空字段就禁止报告。它区分：

- 技术前置条件未完成。
- 影响结论的关键未知。
- 建议补充。
- 可选信息。

用户可以返回补充，也可以选择“继续并在报告中说明缺失”。

## 6.5 Step 5：AI 重要信息提问

用户点击“准备生成报告”后，系统先执行确定性缺失检查，再把允许的项目快照和缺失清单交给 AI。AI 只负责从候选缺失项中挑选值得问的问题，不允许自行扩展到人口、客流、盈利等不可获得信息。

页面以表单方式展示问题，不使用无限聊天：

```text
生成报告前建议补充 2 项信息

1. 候选物业实际月租金是多少？
   [输入金额] [不知道 / 暂不提供]

2. 候选物业可用面积约多少平方米？
   [输入面积] [不知道 / 暂不提供]
```

用户提交答案后保存到项目；选择未知时也保存回答状态。最多两轮，达到限制或用户跳过后必须进入报告步骤。

## 6.6 Step 6：生成和查看报告

生成前冻结本次 `final_project_snapshot`。页面显示生成状态，成功后以业务报告形式渲染。用户可以：

- 查看目录并跳转章节。
- 导出 HTML。
- 浏览器打印 / 保存 PDF。
- 在补充数据后重新生成新版本；旧报告保留生成时的快照，不被新数据悄悄改变。

## 7. 高德自动获取数据范围

## 7.1 地理编码

- 标准化地址。
- 经度、纬度。
- 高德实际返回的行政区字段，仅用于地址确认，不用于推断消费或人口。

## 7.2 周边 POI 分类

### 交通

- 地铁站及出入口。
- 公交站。
- 停车场。
- 高德能够返回且对到店可达性有意义的道路交通设施。

### 疑似竞品

- 电竞馆。
- 网咖、网吧。
- 电竞酒店等可能形成替代竞争的场所。

“疑似竞品”只是高德类别筛选结果，不能自动断定其仍在营业或与目标业态完全相同。

### 餐饮

- 餐馆、快餐、烧烤、夜宵等高德类别或关键词结果。

### 娱乐

- KTV、台球、电影院、酒吧、密室等高德类别或关键词结果。

### 其他

- 高校、职业院校、住宅、公寓等仅作为“周边存在此类 POI”的事实展示。
- 不将其数量换算为人口、年轻人数量或消费能力。

## 7.3 统一映射字段

仅在高德响应中真实存在时映射：

- 名称
- 类别和原始类型编码
- 地址
- 经纬度
- 与项目点的距离
- 电话
- 营业时间
- 评分
- 营业状态
- 采集时间

并非所有高德接口、关键词或商户都会返回电话、评分、营业时间和状态。没有返回时展示“未提供”。

## 7.4 当前代码基线限制

当前 `AmapClient` 对每个关键词只请求第一页，每页最多 20 条，然后进行去重。因此当前数量是“设定关键词下、接口单页范围内的采集结果”，不能宣称完整覆盖。正式实现阶段必须补充分页、总量上限、跨关键词去重和截断提示，并保存分类请求是否成功。

当前统一 POI 映射已经包含名称、类别、地址、坐标、距离和部分营业时间，但电话、评分、营业状态仍需按实际响应审计后映射。不得用默认值冒充高德返回。

## 8. 人工补充数据范围

字段是否保留以“是否影响电竞馆选址”与“用户是否可能真实知道”为标准，不因数据库已有字段而全部保留。

## 8.1 候选物业与租金

### 关键字段

- 可用面积（平方米）。
- 实际月租金（元/月）。
- 楼层和可达方式。
- 供电容量或是否满足设备负载。
- 消防验收/喷淋/排烟/安全出口的已知状态。
- 网络运营商和是否具备双线路条件。
- 是否允许电竞馆/网吧用途及已知物业限制。
- 是否有独立夜间出入口。

### 建议字段

- 物业费。
- 转让费。
- 押金、免租期、租期。
- 停车条件。
- 门头可见性。
- 现场备注和核实日期。

上述信息不知道时可为空。系统不得根据面积或商场名称猜测租金、用电和消防条件。

## 8.2 竞品

### 关键/高价值字段

- 是否确认为真实竞品、是否仍在营业。
- 机器数量。
- 小时价格、会员价格。
- 主要 CPU、GPU、显示器规格。
- 营业时间修正。

### 建议字段

- 面积。
- 开业时间。
- 充值活动。
- 现场观察到的上座率，并同时记录观察日期、时段和调查方式。
- 现场备注。

### 仅在确有来源时填写

- 月营业额或年营业额。

营业额不作为数据准备度必填项，也不作为 AI 必问项。系统不得鼓励用户估算，更不得由 AI 推断。

## 8.3 餐饮与娱乐

默认保留高德基础事实。人工只补充真正影响营业时段判断的信息：

- 是否有效/是否仍营业。
- 营业时间修正。
- 是否经现场确认夜间营业或 24 小时营业。
- 现场备注和核实时间。

不要求逐家填写消费水平、客群画像或经营情况。

## 8.4 明确不采集的人工字段

- 凭感觉填写的区域人口、年轻人口或客流量。
- 推测的消费能力和商圈等级。
- 没有调查依据的竞品上座率、营业额和盈利情况。
- 外部租金市场均价。
- 由餐饮或酒吧数量推导的夜间人流。

## 9. 数据来源与真实性设计

## 9.1 两个正交维度

建议不要把 `FACT` 与 `AMAP_PROVIDED` 混在同一枚举中，而是分为：

### 值状态

- `FACT`：字段有已保存的事实值。
- `UNKNOWN`：没有值，或用户明确选择不知道。

### 来源

- `AMAP_PROVIDED`：高德响应实际返回。
- `USER_PROVIDED`：用户手工填写或回答 AI 问题。
- `CALCULATED`：系统根据事实执行确定性计算，例如数量、最短距离、平均值。

示例：

```json
{
  "hour_price": {
    "value": 10,
    "value_status": "FACT",
    "source": "USER_PROVIDED",
    "observed_at": "2026-08-12",
    "note": "现场询价"
  }
}
```

未知示例：

```json
{
  "occupancy_rate": {
    "value": null,
    "value_status": "UNKNOWN",
    "source": null,
    "unknown_reason": "用户选择暂不提供"
  }
}
```

## 9.2 存储原则

- 高德原始响应可内部留存用于排错，但绝不发送给 AI 或展示给普通用户。
- 人工补充保留修改历史，当前值写回对应业务对象。
- 高德字段和人工字段不能相互覆盖；人工修正需要作为独立的修正值和来源保留。
- 所有计算必须能由输入值重复计算，不能调用 AI 生成数值。
- 待审核、已拒绝、演示模拟、爬虫和旧第三方数据不得进入 MVP 最终快照。

## 9.3 最终项目快照

建议结构：

```json
{
  "snapshot_version": "amap-manual-ai-mvp-v1",
  "generated_at": "ISO-8601",
  "project": {},
  "amap_collection": {
    "status": "completed",
    "collected_at": "ISO-8601",
    "category_results": []
  },
  "traffic": [],
  "competitors": [],
  "food": [],
  "entertainment": [],
  "property_and_rent": {},
  "calculated_summary": {},
  "missing_data": [],
  "ai_question_answers": []
}
```

每个可用于结论的字段必须携带来源；快照不包含内部 `confidence`、`provider_status`、`raw_data`、工具日志或其他外部数据。

## 10. 数据核验机制

## 10.1 数据准备度

数据准备度是已完成清单的百分比，不是可信概率。计算规则必须公开、固定、可测试。

建议分组：

- 地址与采集基础：30%。
- 竞品基础事实：25%。
- 核心竞品人工调查：20%。
- 候选物业与租金：20%。
- 配套人工核实：5%。

实际权重在实施阶段通过真实案例确认，但不得由 AI 动态修改。

## 10.2 关键前置条件

- 有城市、详细地址和分析半径。
- 地理编码成功或用户确认了候选坐标。
- 高德采集已执行，并能区分“真实零结果”和“请求失败”。

上述条件缺失时仍可生成“数据不足”说明，但不能给出推荐/不推荐投资结论。

## 10.3 关键未知

对推荐等级影响较大的未知信息，例如：

- 候选物业实际租金和面积。
- 物业用途、消防、供电和网络条件。
- 最近核心竞品是否有效以及基本价格/规模。

## 10.4 建议补充

- 部分竞品配置、会员价、充值活动。
- 餐饮/娱乐营业时间修正。
- 停车、门头等现场信息。

## 10.5 可选信息

- 竞品开业时间。
- 有可靠来源的竞品营业额。
- 其他不改变核心判断的备注。

任何缺失都必须以普通业务语言展示，不出现 `confidence=0.73`、Provider 状态或原始 JSON。

## 11. AI 提问机制

## 11.1 处理顺序

1. 系统确定性检查数据。
2. 生成允许提问的缺失候选清单。
3. AI 只能从该清单选择问题，并输出结构化 JSON。
4. 后端验证问题对应字段确实缺失、用户可能知道、没有重复询问。
5. 前端以表单展示。
6. 回答写入业务字段；“不知道”写入问题回答记录并停止重复询问。

## 11.2 提问限制

- 默认一轮，最多两轮。
- 每轮最多 3 个问题，总计最多 5 个。
- 第二轮仅在第一轮答案暴露了新的直接依赖时触发。
- 用户可随时选择“跳过并生成报告”。
- 达到轮次上限后必须停止提问。

## 11.3 问题准入条件

问题必须同时满足：

- 与当前候选地址的电竞馆选址直接相关。
- 当前最终快照确实没有答案。
- 用户通过合同、物业沟通或现场调查可能知道。
- 答案会显著影响报告结论或现场核实清单。

禁止询问用户无法合理知道的宏观人口、真实客流、区域消费能力和盈利预测。

## 11.4 建议输出结构

```json
{
  "round": 1,
  "questions": [
    {
      "id": "property.monthly_rent",
      "field_key": "property.monthly_rent",
      "question": "候选物业实际月租金是多少？",
      "reason": "租金会影响成本压力判断",
      "answer_type": "money",
      "required": false
    }
  ]
}
```

若没有值得问的问题，返回空列表并直接进入报告。

## 12. AI 报告结构

## 12.1 项目概况

- 地址、分析范围、生成时间。
- 已掌握的数据类别和准备度。
- 数据来源说明。

## 12.2 核心结论

结论只允许：

- 推荐
- 谨慎
- 不推荐
- 数据不足

必须用已知事实解释原因。若关键前置条件或物业核心事实不足，结论必须为“数据不足”，不得仅靠 POI 数量给出投资推荐。

## 12.3 交通环境

只使用高德返回的地铁、公交、停车场和距离等事实。不得把交通 POI 数量直接等同于实际客流。

## 12.4 竞争环境

- 疑似竞品数量、距离和分布。
- 已人工确认的价格、机器数量、配置和现场上座率。
- 对没有数据的维度明确写“无法判断”。

## 12.5 周边商业配套

描述高德餐饮、娱乐和夜间相关 POI 的数量、类型、距离，以及人工确认的营业情况。不得据此推导年轻人口、消费转化率或夜间客流。

## 12.6 物业与租金

只分析用户实际填写的物业、租金、供电、消防和网络事实。无数据时逐项说明未知。

## 12.7 数据缺失与风险

- 数据充分 / 数据一般 / 数据不足。
- 哪些判断有直接事实支持。
- 哪些判断因缺失无法完成。
- 高德 POI 可能存在收录和营业状态滞后的边界。

## 12.8 最终建议

严格分成两组：

1. 基于已有事实可以确定的结论。
2. 签约或投资前仍需现场核实的事项。

## 13. 禁止 AI 猜测规则

AI Prompt、快照构建和输出校验必须共同执行以下规则：

- `UNKNOWN` 不能推导为事实。
- 不得使用“预计”“可能约”“一般情况下”“据经验”来补不存在的数值。
- 不得根据地名或 POI 推测人口和年龄结构。
- 不得根据餐饮、酒吧或高校数量推测消费能力和真实客流。
- 不得预测营业额、上座率、盈利、回本周期和消费转化率。
- 不得推测租金或城市租金水平。
- 不得把疑似竞品数量解释为实际有效竞品数量，除非有人工作业确认。
- 不得把系统没有提供的行业标准、外部知识写成当前项目事实。
- 不得自行联网或调用其他工具。
- 报告中的每个数字必须存在于最终快照或可由快照确定性计算。

若用户询问系统没有的数据，标准回答是：

> 当前项目数据中没有该项信息，因此无法判断。建议通过现场调查或可靠资料补充后再分析。

## 14. 系统配置范围

普通配置页只保留：

- 高德 Web Service Key。
- DeepSeek API Key。
- DeepSeek Base URL。
- DeepSeek Model。

要求：

- Key 加密保存且不回显完整值。
- 保存和连接测试均有明确成功/失败反馈。
- 已配置时按钮和状态清晰变化。
- 管理员令牌属于部署安全机制，不作为普通使用者反复填写的产品配置。

当前高德 JS Key 和安全密钥只服务于前端地图组件。MVP 不以交互地图为必需能力；普通配置页应隐藏。如果保留地图展示，应将其作为部署高级配置，并确保缺少 JS Key 时核心六步流程仍可用。

以下配置全部从普通配置页隐藏：

- Crawler
- Third Party Provider
- 政府公开数据
- Memory
- 评分维度与动态权重
- Trace / Debug / Reflection

## 15. 当前代码基线与产品方向冲突

当前仓库已经超过新 MVP 所需范围，主要冲突包括：

1. 后端 `main.py` 同时注册项目、高德、竞品、配套、租金、爬虫、政府统计、Memory、复杂评分、Agent、Trace、反馈、Demo 和经营结果等路由。
2. 数据库同时存在旧 `site_evaluations` 链路和新 `site_projects` 链路，形成两套项目/报告模型。
3. 前端既有新的 Workbench，也保留 `/projects/:id` 详情、旧评估、Agent、历史、独立报告等大量可直接访问路由。
4. Workbench 同时承担项目、8 步流程、爬虫、AI 审核、评分、报告、聊天、维度、数据源和 Memory，信息层级过重。
5. SystemConfig 暴露第三方、爬虫、政府数据、评分和 Memory 配置，超出普通用户需要。
6. 当前数据质量逻辑把爬虫、政府数据、模拟数据和复杂评分混在一起，并把竞品营业额列入缺失项，容易诱导不可靠补充。
7. AI 上下文包含评分、城市洞察、Memory、爬虫证据和模拟摘要，不符合“只读高德 + 人工 + 确定性计算”的边界。
8. 当前 AI 数据审核返回 Markdown 结论，不是有轮次限制、可校验、可写回字段的结构化提问流程。
9. 当前迁移 `0014_backfill_amap_business_hours` 的 revision 长度超过 Alembic 默认 `version_num VARCHAR(32)`，已经造成生产部署风险；必须作为实施前基线问题处理，但本次文档阶段不修改。

## 17. 验收标准

### 17.1 产品范围

- 主导航和普通用户页面只出现项目流程与系统配置。
- 页面不出现爬虫、第三方、热力、Memory、Agent、Trace、Tool、Debug、Provider、Confidence。
- 核心流程缺少爬虫和政府数据时完全可运行。

### 17.2 高德采集

- 输入真实地址能够完成地理编码并确认坐标。
- 分页采集覆盖设定关键词，跨关键词去重。
- 页面显示实际保存的唯一记录数、分类数量、失败分类和截断情况。
- 电话、评分、营业时间等只在响应真实存在时展示。
- 能区分请求失败与真实零结果。

### 17.3 人工补充

- 从高德竞品条目进入补充，名称、地址、距离无需重复填写。
- 保存后更新同一条业务记录并保留人工来源和修改历史。
- 空字段和“不知道”均被允许。
- 人工字段不覆盖高德原始事实。

### 17.4 数据检查

- 普通业务用户能看懂已完成、关键未知、建议补充和可选信息。
- 准备度规则固定、可解释、可测试。
- 不显示内部置信度、Provider 或 raw JSON。
- 缺少非关键字段不会阻止生成报告。

### 17.5 AI 提问

- 问题对应真实缺失字段且不重复。
- 最多两轮，每轮最多 3 题，总数不超过 5。
- 用户可选择“不知道 / 暂不提供”或直接跳过。
- 回答进入最终快照并标记 `USER_PROVIDED`。

### 17.6 AI 报告

- 报告包含本 PRD 规定的八个章节。
- 报告数字能够逐一在最终快照中找到或重复计算。
- `UNKNOWN` 不被补全或推导。
- 没有上座率、租金、人口或客流时明确写无法判断。
- 关键数据不足时结论为“数据不足”。
- HTML 导出和打印 PDF 内容完整、排版可读。

### 17.7 稳定性与安全

- 全量后端测试、前端测试和构建通过。
- Alembic 只有一个 head，新库可从零升级，现有库可无损升级。
- Key 不出现在接口响应、日志、快照、报告或 Git 中。
- 真实地址验收覆盖正常、歧义、零结果、部分接口失败和大量 POI 场景。

## 18. 本 PRD 确认后的执行原则

- 严格按实施计划逐阶段执行，每阶段单独验收。
- 先隐藏再删除，先统一用户流程再清理底层历史。
- 不在重构过程中顺带增加新数据源或新 Phase。
- 任何新增字段先证明其对电竞馆选址有实际作用。
- 产品结论服从数据真实性，不以“看起来完整”为目标编造内容。
