## P1 快赢（1–2 周，低风险，立即可用）

### P1.1 夜间经济打标（夜间营业 POI 列表）
- **目标**：电竞馆核心是夜间客流，把「22:00 后仍在营业」的餐饮/便利店/KTV 自动识别并列表展示。
- **数据**：基于已修复的 `business_hours`（`converters._amap_business_hours`）。新增统一解析函数 `night_business_parser`：
  - `24小时` / `00:00-24:00` / `00:00-23:59` → 全天候；
  - 结束时间 ≥ 22:00（如 `10:00-04:00`、`17:00-02:00`）→ 夜间营业；
  - 无法判断 → 标记「待人工核实」，不猜测。
- **后端**：`backend/app/data_model/converters.py` 增加 `infer_night_business(business_hours) -> bool | None`；`UnifiedPOIRecord` 增加 `night_business` 列（0015 迁移）；`dataset` 返回按夜间营业过滤。
- **前端**：人工补充页 POI 列表按「夜间营业 / 普通 / 待核实」筛选项 + 高亮 Tag。
- **验收**：西部电子社区项目 80 条 POI 中，夜间营业识别率与人工抽检 10 条一致；无 `business_hours` 的条目不产生误判。
- **测试**：单测覆盖 24 小时、跨零点、无时间三种输入。

### P1.2 竞品压力指数
- **目标**：把散落的竞品字段综合成一个「竞品压力指数（0–100）」，取代零散字段对比。
- **公式（可配置权重）**：`指数 = w1·数量密度 + w2·距离分 + w3·机位分 + w4·价格分 + w5·上座率分`
  - 数量密度：500m/1000m 内有效竞品数；
  - 距离分：距离越近压力越大（分段函数，非简单线性）；
  - 机位分：总机位越多压力越大；
  - 价格分：竞品均价越低，目标馆定价空间越小；
  - 上座率分：已核实上座率越高压力越大。
- **后端**：新增 `backend/app/scoring/competitor_pressure.py`（纯函数，便于单测）；纳入评分维度 `competitor_environment` 的说明字段；报告上下文输出竞品压力排名列表。
- **前端**：Step 3 竞品 Tag 旁显示「压力指数」；报告页输出「竞品压力 TOP 10」。
- **验收**：给定固定竞品数据，指数可复现；缺失字段按保守默认值（不放大也不忽略），并标记数据质量影响。
- **测试**：10 组固定样例断言指数排序符合业务直觉。

### P1.3 夜间交通提示
- **目标**：夜间（22:00 后）通宵客群能否往返，直接影响电竞馆开业决策。
- **数据**：地铁末班车时间 + 公交夜班线路（公共来源，人工确认兜底）。
- **实现**：
  - 人工补充页新增「夜间交通」区块：最近地铁站末班车时间、是否夜班公交、步行距离；
  - 高德 POI 已有地铁站距离（`transport` 分类），末班车时间走人工/已确认爬虫数据，不猜。
- **验收**：报告「夜间消费」维度描述包含夜间交通结论；数据缺失时明确提示。

## P2 核心（3–6 周，中风险）

### P2.1 可承受租金测算
- **目标**：从「租金样本对比」升级为「盈亏平衡驱动的可承受租金上限」。
- **模型**（纯函数，人工输入为主，不依赖大模型推算）：
  - 收入侧：`月收入 ≈ 机位数 × 小时价 × 日均上座率 × 日均营业时长 × 30 × (1+餐品/会员附加系数)`
  - 成本侧：租金 + 物业 + 人力 + 电费(电竞高功耗) + 折旧 + 杂费
  - 输出：`可承受月租金 = 月收入 − 其他成本 − 目标利润率`
- **后端**：`backend/app/scoring/rent_affordability.py`；报告上下文输出「可承受租金区间 + 假设条件」。
- **前端**：租金补充表单增加「假设参数」折叠区；报告页生成租金额度参考线。
- **验收**：输入可变参数可重算；报告中所有数字标注「估算」来源，禁止表述为真实成交数据。
- **测试**：单元测试覆盖不同上座率/机位数敏感性。

### P2.2 客群可视化
- **目标**：把大学/高职/公寓/年轻住宅渲染到地图，量化「500m 内年轻客群代理指标」。
- **数据**：高德 `education`/`residential` 分类 POI + 人工补充客群信息（不显示为真实人口，遵守 AGENTS.md）。
- **实现**：
  - 前端引入高德 JS 地图图层（已有 `amapJsKey`），按分类着色 POI；
  - 新增「客群代理指数」说明：仅代表学校/公寓数量与距离代理，不替代人口数据。
- **验收**：地图能按分类筛选；任何人口数字都有「代理指标」标识。
- **依赖**：`frontend-runtime.json` 的高德 JS Key 配置已具备。

### P2.3 多候选点对比
- **目标**：一次评估 2–3 个候选地址，同屏对比综合分与维度雷达图。
- **后端**：`对比快照` 表（0016 迁移）存各项目评分结果 + 维度分；对比接口只读。
- **前端**：新增「方案对比」页：选择项目 → 并排展示综合分、12 维度条形图、风险项交集/差异。
- **验收**：对比页面所有数字来自各项目已保存评分，实时重算不覆盖原项目。
- **测试**：对比 API 幂等，删除任一项目后对比不报错。

## P3 高级（7–12 周，高风险高价值）

### P3.1 移动端现场调查（App/小程序）
- **目标**：现场调研用手机拍照、语音、快捷录入，替代纯网页表单。
- **范围**：PWA 优先（复用现有 API + 高德定位），后续可打包小程序。
- **能力**：GPS 定位绑定项目、竞品现场拍照上传、语音转文字备注、离线草稿。
- **验收**：弱网/离线可保存草稿，恢复后自动同步；图片与记录关联项目且不泄露位置敏感信息。
- **注意**：新增能力必须模块化扩展并配套测试与文档。

### P3.2 第三方 LBS 客流数据接入
- **目标**：补齐「1km 真实人口、小时客流、客群画像」缺口。
- **实现**：通过 `DataProvider` 抽象新增 `lbs` 数据源（百度慧眼/腾讯位置服务/和鲸等授权数据），接入协议遵守合规要求。
- **边界**：授权数据的口径、时间戳、去重与置信度全部保留在 `raw_data`；城市宏观数据不得冒充项目级客流。
- **验收**：数据源状态页显示授权状态与有效期；评分只在有真实授权数据时启用对应维度。
- **依赖**：需要客户侧商务授权，属阻塞性前置条件。

### P3.3 大模型辅助解释升级
- **目标**：在数据治理完善后，让 AI 解释「为什么这个点位适合/不适合」并回测历史选址结论。
- **范围**：仅基于已确认数据结构化输出；禁止生成不存在的经营数据；所有结论可溯源到数据行。
- **验收**：报告每一条结论都有数据来源引用；含估算/推断处强制标注。

## 测试与验收口径
- 每个功能：后端单测（纯函数优先）+ 前端 vitest + `npm run build` 通过。
- 数据口径：估算/代理/授权数据必须显式标注，人工调查与高德基础数据分层存储。
- 回归：每次合入跑 `backend/tests` 全量用例，确保 240+ 用例不回归。
