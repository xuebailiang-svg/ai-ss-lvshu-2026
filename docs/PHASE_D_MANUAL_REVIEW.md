# Phase D 人工补充模型与界面实施记录

## 1. 实施结论

Phase D 已将人工核实收敛到统一页面，并保持“高德事实层”和“人工补充层”分离。已有高德记录不会因人工编辑而改写来源，重新采集也不会覆盖人工补充字段。

本阶段未新增数据库表或字段，复用现有 `raw_data` JSON、`manual_inputs` 和 `supplements`，因此没有新增 Alembic migration。

## 2. 页面调整

统一人工补充入口为 `ProjectSupplement`：

- 竞品：名称、地址、距离和高德来源只读；默认按距离排序；支持名称搜索和只看待补充。
- 竞品详情：规模配置、价格、营业信息、现场上座率及观察时间/时段/方式、可靠营业额来源和备注分组编辑。
- 配套：仅补充有效状态、营业时间、夜间营业/24 小时、类型和备注。
- 候选物业：集中填写地址、面积、月租、楼层、用途、供电、消防、网络和独立入口。
- 租金：展示已有候选租金记录并允许修正核心字段和物业条款。
- 所有表单支持明确标记“不知道”，保存成功后显示字段来源、核实时间与历史次数。

旧 `DataCollectionCenter` 不再承担第二套审核表格，只保留采集数量概览和进入统一人工整理页的入口。

## 3. 数据写入规则

```text
高德采集字段（只读）
  + 人工补充字段（raw_data.manual_detail）
  + 字段级来源/未知/时间/摘要历史（raw_data._manual_meta）
  + 完整字段审计（manual_inputs）
```

规则如下：

1. 已有记录的 `source=amap` 保持不变。
2. 人工字段只写空白或人工覆盖层，不修改高德原始响应。
3. `unknown_fields` 是用户明确选择的状态，可增加也可取消。
4. 状态审核和字段修改都写入审计记录。
5. 候选物业使用 `supplements` 中唯一的 `candidate_property/primary` 记录做幂等更新。
6. 营业额不是必填项；只有存在可靠来源时才建议填写。

## 4. API 契约变化

竞品、配套和租金详情响应新增：

```json
{
  "manual_meta": {
    "field_sources": {"machine_count": "manual"},
    "unknown_fields": ["member_price"],
    "verified_at": "2026-08-12T00:00:00+00:00",
    "history_count": 2
  }
}
```

详情更新请求可传：

```json
{
  "unknown_fields": ["member_price"]
}
```

传空数组会取消之前的未知标记；省略该字段则保持原状态。

通用人工录入接口新增 `type=property`，用于幂等保存候选物业。竞品通用录入也改为写入人工覆盖层，不再把已有高德记录的来源改成 `manual`。

## 5. 第一版边界

- 不使用 AI 自动填写人工调查数据。
- 不展示或恢复爬虫建议、第三方证据和模拟数据。
- 不要求人口、消费、营业额或盈利预测。
- 不自动确认全部高德候选。
- 暂不增加“高德未收录对象”创建入口。第一版优先保证高德候选与人工核实一一关联，避免再次产生重复记录；确有遗漏时可在后续独立需求中增加受控人工对象。

## 6. 验证范围

- 竞品、配套、租金和候选物业保存。
- 字段来源、未知状态、取消未知及修改历史。
- 旧通用人工接口不覆盖高德记录来源。
- 前端人工补充页面 TypeScript 构建。
- 前端路由与 Markdown 报告回归测试。
- 全量后端回归测试。
